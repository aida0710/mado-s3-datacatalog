APIの形を兄弟製品のmado ML Trackingとそろえました。DBの移行は`api-internal`が起動時に当てるようになり、手で移行を当てる手順はなくなりました。アクセストークンの前置きは`mado_dc_`になり、発行済みのトークンは再発行が要ります。一覧のページ送りは`cursor`/`nextCursor`に、ヘルスチェックはJSONになりました。APIの仕様を[`docs/openapi.json`](https://github.com/aida0710/mado-s3-datacatalog/blob/v0.5.0/docs/openapi.json)（OpenAPI 3.1）で公開します。

## 変更点

- **DBの移行の自動適用**: `api-internal`は起動時に、DBの管理者の接続（`DATABASE_URL_MIGRATE`。Composeが`POSTGRES_PASSWORD`から組み立てる）で未適用の移行を当て、`schema_migrations`に名前とSHA-256を記録します。同時に起動しても`pg_advisory_lock`で1回だけ当たります。当てた後のファイルの書き換えや、記録の無いまま表があるDBでは起動しません。`api-lineage`と`media-worker`は移行を当てる権限を持たず、全部当たっていることを確かめてから起動します。移行のファイルは`mado-api`のイメージに入り、Postgresの初期化スクリプトはロールとテスト用DBだけを作ります。
- **アクセストークンの前置き**: 値は`mado_dc_<16桁>.<秘密>`になりました（mado ML Trackingは`mado_mt_`）。`mado_lin_`で始まる値は受け付けません。
- **ページ送り**: 続きのある一覧は`cursor`（中身の見えない文字列）で読み、応答の`nextCursor`を次の要求へそのまま渡します。`null`なら最後のページです。読めない値は400 `invalid_cursor`です。
  - 監査ログ`GET /api/internal/audit-events`: `beforeId`/`nextBeforeId`をやめました。
  - DataLineageの登録一覧`GET /api/internal/lineage/catalog`: `offset`をやめ、応答に`nextCursor`を足しました。
  - ディレクトリの一覧`GET /api/internal/storage/{connectionId}/list`: `continuation`・`startAfter`/`nextContinuation`・`nextStartAfter`をやめました。
  - 連携用の`GET /api/mado/lineage/catalog`は、mado ML Trackingが`offset`で呼ぶため変えていません。tarの中身の一覧（`preview/tar`）も`offset`/`limit`のままです。
- **ヘルスチェック**: `api-internal`・`api-lineage`・`media-worker`の`GET /healthz`は、DBに届けば200と`{"status":"ok"}`、届かなければ503と`database_unavailable`を返します（以前は文字列`ok`）。Composeに3つのhealthcheck（`node dist/scripts/healthcheck.js <ポート>`）を足し、`api-lineage`・`media-worker`・Webは`api-internal`がhealthyになってから起動します。
- **APIのお知らせのcode**: 見積もりの注意は`{kind, message}`（日本語の文）をやめ、`{code, 値の項目}`（日数・単価・バイト数・件数・割合）を返します。DataLineageの警告は文字列の配列から`{code}`の配列に、グラフの反映状態を取れなかった理由は`projection.code`になりました（Dataset Registryが返す説明は`projection.message`のまま）。単価カタログの手入力の注記も`code`になりました。画面はどれもcodeで訳します。
- **入力の誤りの表示**: `invalid_request`は、英語の画面ではAPIの英語の文をそのまま、日本語の画面では「入力内容を確認してください。」の後にAPIの文を括弧で添えます。
- **OpenAPI**: `docs/openapi.json`をルートの一覧（`api/openapi/route-catalog.ts`）から作り、実際のルートとのずれをテストで見つけます。応答のスキーマは`api/shared/schemas/`に置き、画面と共有します。

## 互換性と更新手順

更新前にDBをバックアップしてください。**v0.4.0までのDBには`schema_migrations`が無いので、最初の起動の前に一度だけ記録の手順が要ります。** 記録をせずに新しい`api-internal`を起動すると、移行を当てずに止まります。

1. 運用中のCompose（`compose.yaml`、MDXでは`compose.mdx.yaml`）を直します。
   - `api-internal`の`environment`に`DATABASE_URL_MIGRATE: "postgres://postgres:${POSTGRES_PASSWORD}@postgres:5432/dashboard"`を足します。`POSTGRES_PASSWORD`はURLにそのまま入る値（hex）にしてください。既存のDBのパスワードにURLで意味を持つ文字（`@` `:` `/` `?` `#` `%`など）が入っているなら、先に`ALTER ROLE postgres PASSWORD '<hexの値>'`で替え、`.env`の`POSTGRES_PASSWORD`も同じ値にします（`.env`を変えるだけでは既存のDBに効きません）。
   - `api-internal`（ポート3000）と`api-lineage`（3001）に`healthcheck`（`["CMD", "node", "dist/scripts/healthcheck.js", "<ポート>"]`）を、`deploy/worker-service.yaml`の`media-worker`に3100のhealthcheckを足します。
   - `api-lineage`と`media-worker`の`depends_on`に`api-internal: { condition: service_healthy }`を、Webの`depends_on`を両APIの`service_healthy`にします。
   - `postgres`の`./db/migrations:/migrations:ro`のマウントは使わなくなったので外します。
   - 配布物の`compose.yaml`と`deploy/worker-service.yaml`は、これらを含んでいます。
2. Composeの`api-internal`の`image`をこの版（digest）にして取得し、v0.4.0（`041`）まで当ててあるDBを一度だけ記録します。SQLは実行しません。`run`は手順1で足した`DATABASE_URL_MIGRATE`を使うので、手順1の後に行います。

   ```bash
   docker compose -f compose.yaml run --rm --no-deps api-internal \
     node dist/scripts/record-applied-migrations.js --through 041
   ```

3. `api-internal`をこの版で起動し、healthyになるまで待ちます。起動時に`042`〜`045`が当たります。`api-lineage`・`media-worker`・Webを`--no-deps`で同時に作り直すと、移行が終わるまで起動と停止を繰り返すので、`api-internal`を先にしてください。
   - 042: これまで初期化スクリプトが行っていた所有者と読み取り権限の設定を移行にしました。既存のDBで`dashboard_ro`に読み取りの権限が無い表があれば、読めるようにします（`dashboard_ro`は`dashboard_rw`と同じパスワードのロールです）。
   - 043: 発行済みのトークンの前置きを`mado_dc_`に替え、秘密を使えない値に置き換えます。
   - 044: 古い形のディレクトリの一覧のキャッシュを消します。最初に開いたディレクトリはS3から取り直します。
   - 045: 文で注記を持っていた取得済みの単価カタログを消します。取り直すまでは同梱のカタログで見積もり、次に見積もりを開いたときに裏で取り直します。
4. `api-lineage`・`media-worker`・Webをこの版で起動します（MDXではこれまでどおり`nginx`と`edge`をreloadします）。
5. **アクセストークンを再発行します。** Settings → Access → Access Tokensで各トークンの**再発行**を選び、新しい値を連携先へ配ります。名前・権限・Namespace・有効期限・状態はそのままです。Prometheusの`credentials_file`、mado ML Trackingの［連携］のアクセストークン、OpenLineageを送るPipelineの設定を更新してください。
6. `/healthz`を文字列`ok`で確かめている監視があれば、HTTPの状態か`{"status":"ok"}`で確かめるように直します。

`api-internal`はDBの管理者（`postgres`）の接続を持つようになります。`api-lineage`と`media-worker`には渡しません。

この版から戻すときは、043の後なのでv0.4.0ではアクセストークンを使えません（v0.4.0は`mado_lin_`だけを読み、`mado_dc_`の行を作れません）。DBを戻さずにv0.4.0へ戻すのは、トークンを使わない確認のためだけにしてください。

## 配布物

Linux amd64/arm64向けの`mado-api`、`mado-media-worker`、`mado-web`をGHCRで配布します。添付の`mado-v0.5.0.tar.gz`には、digest固定のCompose、DBのロールを作る初期化スクリプト、設定例、導入手順が入っています。DBの移行は`mado-api`のイメージに入っています。SHA-256チェックサムとビルド証明も公開します。

互換Dataset Registryとその認証トークンは引き続き別途必要です。[ドキュメント](https://aida0710.github.io/mado-s3-datacatalog/)、[DBの手順](https://github.com/aida0710/mado-s3-datacatalog/blob/v0.5.0/db/README.md)、[APIの仕様](https://github.com/aida0710/mado-s3-datacatalog/blob/v0.5.0/docs/openapi.json)を参照してください。
